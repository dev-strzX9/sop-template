SOP Studio 는 어떻게 돌아가나

서버가 켜지는 순간부터, 브라우저에서 "저장" 을 누른 요청 하나가 DB 에 들어갔다가 응답으로 돌아올 때까지를 순서대로 따라갑니다. 각 장면마다 무엇을 하는지와 왜 이렇게 만들었는지를 같이 적었습니다.

1부 · 큰 그림0. 이 문서 읽는 법

위에서 아래로 쭉 읽으면 하나의 이야기가 되도록 썼습니다. 1부에서 전체 모양을 잡고, 2부에서 서버가 켜지고, 3부에서 요청 하나가 들어와 응답이 나가고, 4부에서 그 요청이 DB 안에서 무슨 일을 하는지, 5부에서 화면 쪽은 어떻게 생겼는지, 6·7부에서 앞으로 붙일 것과 운영을 다룹니다.

표시 세 가지만 기억하세요.

1부 · 큰 그림2. 세 덩어리와 그 사이의 연결

덩어리는 셋입니다. ① 브라우저에서 도는 HTML/JavaScript, ② 파이썬 서버, ③ PostgreSQL. 브라우저는 DB 를 직접 만지지 않고 반드시 서버를 거칩니다.

왜?

왜 브라우저가 DB 에 직접 붙지 않나 — 브라우저 코드는 사용자가 개발자 도구로 얼마든지 고칠 수 있습니다. 검사(형식, 충돌, 권한)를 브라우저에만 두면 우회됩니다. 서버가 "문지기" 이고, DB 비밀번호도 서버만 압니다.

왜 HTML 도 같은 서버가 내려주나 — 화면과 API 가 같은 주소(origin)에서 나오면 CORS 설정이 필요 없고, 배포 단위가 컨테이너 하나로 끝납니다. 📍 app/main.py:169 index() 가 static/sop/sopstudio.html 을 읽어 보냅니다.

왜?

왜 core 와 sop 를 나눴나 — OPL, 주간보고가 추가될 예정이기 때문입니다. 공통(설정, DB, 사용자, 오류)은 한 번만 만들고 업무는 옆에 폴더로 붙입니다. 규칙은 하나: core/ 안에 "SOP" 라는 단어가 나오면 안 됩니다. 그 규칙만 지키면 업무끼리 서로를 몰라도 됩니다.

왜 derive.py 는 DB 를 안 쓰나 — "JSON 을 받아 행을 돌려준다" 만 하는 순수 함수라 DB 없이도 테스트할 수 있습니다. 편집기 JSON 의 키 이름이 바뀌면 이 파일만 고치면 됩니다.

왜 sops / versions / locks 로 나눴나 — 쓰기(sops), 읽기 전용 이력(versions), 잠금(locks)은 바뀌는 이유가 서로 다릅니다. 같이 쓰는 작은 함수는 common.py 에 모아 중복을 없앴습니다.

2부 · 서버가 켜지기까지4. 설정: .env 와 환경변수

서버가 켜지려면 먼저 "어느 DB 에 붙을지, 몇 번 포트를 열지" 를 알아야 합니다. 이런 값은 코드에 적지 않고 환경변수(운영체제가 프로그램에 건네는 이름=값 쌍)로 받습니다.

# app/__init__.py  📍 app/__init__.py:9
load_dotenv(os.path.join(프로젝트폴더, ".env"))      ← .env 파일 내용을 환경변수로 "올림"

# app/core/config.py
self.user_header = os.environ.get("USER_HEADER", "X-User")   ← 이름으로 꺼내 씀, 없으면 기본값
왜?

왜 환경변수인가 — 같은 코드를 내 PC(로컬 DB, 8000번)와 회사(10.61.41.6, 5000번)에서 고치지 않고 돌리기 위해서입니다. 코드는 "이름" 만 알고, 값은 실행하는 곳이 넣어 줍니다.

왜 .env 파일인가 — 회사 규칙입니다(설정은 .env + load_dotenv). 환경변수를 매번 손으로 치는 대신 파일에 적어 두는 메모장입니다.

왜 load_dotenv 가 덮어쓰지 않게(override=False) 했나 — 배포 설정(Dockerfile ENV, deployment.yaml)이 .env 보다 우선해야 운영자가 이미지를 다시 빌드하지 않고 값을 바꿀 수 있기 때문입니다.

왜 app/__init__.py 에 두었나 — app 패키지의 무엇을 import 하든 이 파일이 가장 먼저 실행됩니다. 그래서 "설정을 읽기 전에 .env 를 올리는 것을 깜빡" 하는 일이 생길 수 없습니다. app.py 맨 위의 import app 도 PORT 를 읽기 전에 .env 를 올리려는 줄입니다.

왜 get_settings() 가 부를 때마다 새로 읽나 — 테스트에서 환경변수를 바꿔 끼운 효과가 바로 보이게 하려는 것입니다. 값이 몇 개 안 되어 비용은 무시할 만합니다.

왜 DATABASE_URL 과 PGHOST 두 방식인가 — 로컬은 주소 한 줄이 편하고, 회사는 호스트·계정·비밀번호를 따로 주는 경우가 많습니다. 조립에는 make_conninfo 를 써서 비밀번호에 @, / 같은 특수문자가 있어도 안전합니다. DATABASE_URL 이 있으면 그것이 최우선이므로 회사에서 PGHOST 방식을 쓰려면 DATABASE_URL 줄을 지워야 합니다.

2부 · 서버가 켜지기까지5. 시작 순서

# app.py (요약)  📍 app.py:28
import app                                   ① .env 올리기
def main():
    if sys.platform == "win32": ...          윈도우만: 이벤트 루프 방식 변경
    apply_schema(get_settings().database_url)   ② DB 표 준비
    port = int(os.environ.get("PORT", "8000"))
    uvicorn.run("app.main:app", host="0.0.0.0", port=port,
                proxy_headers=True, forwarded_allow_ips="*")   ③ 웹서버 → ④ main.py 읽기 → ⑤ lifespan
왜?

왜 python app.py 인가 (uvicorn 명령이 아니라) — 회사 컨테이너 규칙이 "python app.py 로 시작" 입니다. 그래서 uvicorn 실행을 파이썬 코드 안으로 옮겼습니다.

왜 DB 표 준비를 서버보다 먼저 하나 — 표가 없는 상태로 서버가 뜨면 첫 요청마다 500 이 납니다. 먼저 준비하고, 준비가 안 되면(접속 실패) 서버를 아예 켜지 않아야 원인이 로그 첫 줄에 바로 보입니다.

왜 host="0.0.0.0" — 127.0.0.1 로 열면 같은 컴퓨터 안에서만 접속됩니다. 컨테이너 밖(플랫폼, 다른 PC)에서 들어오려면 모든 주소에서 받아야 합니다.

왜 proxy_headers=True — 회사에서는 앞단 프록시가 https 를 처리하고 우리 서버엔 http 로 넘깁니다. 프록시가 붙이는 X-Forwarded-Proto 등을 믿어야 서버가 "원래 https 였다" 를 압니다.

왜 윈도우만 따로 — 윈도우의 기본 비동기 방식(Proactor)은 psycopg 비동기 연결과 맞지 않아 접속이 실패합니다. 맥·리눅스에서는 지나가는 줄입니다.

2부 · 서버가 켜지기까지6. DB 표 준비 (apply_schema)

📍 app/core/apply_schema.py:113 — MODULES = (("sop", "sop_documents"),) 에 적힌 업무마다 기준 표가 있는지 보고 갈림길을 고릅니다.

왜?

왜 "멱등" 마이그레이션인가 — 보통은 "몇 번 마이그레이션까지 적용했다" 는 기록 표를 둡니다(Alembic 등). 여기서는 표를 몇 개 안 바꾸므로, 대신 모든 마이그레이션을 IF NOT EXISTS, IF EXISTS 로 써서 매번 전부 다시 돌려도 결과가 같게 했습니다. 도구가 단순해지는 대신, 마이그레이션을 쓸 때 항상 멱등으로 써야 한다는 약속이 생깁니다.

왜 새 설치는 schema.sql 한 방인가 — 새 DB 에 001, 002 를 차례로 쌓는 것보다 "최종 모양" 한 파일이 읽기 쉽습니다. 그래서 schema.sql 은 항상 최신 모양이고, 001(ref_document_id 추가)·002(sop_drafts 삭제)는 그 이전에 만든 옛 DB 를 위한 것입니다. 지금 schema.sql 로 만든 DB 에서는 아무 일도 하지 않습니다.

왜 pg_trgm 이 없어도 진행하나 — 회사 DB 에서 CREATE EXTENSION 권한이 없는 경우가 흔합니다. pg_trgm 은 "이름 부분 검색" 을 빠르게 하는 인덱스용이라, 없으면 그 줄만 빼고 진행합니다. 기능은 같고 속도만 다릅니다.

왜 이 도구는 동기(psycopg.connect)인가 — 서버가 뜨기 전에 한 번 도는 스크립트라 비동기가 필요 없습니다. python -m app.core.apply_schema --dry-run 처럼 따로 실행할 수도 있습니다.

2부 · 서버가 켜지기까지7. 연결 풀과 lifespan

uvicorn 이 app/main.py 를 읽으면 위에서부터 차례로 로그 설정 → app = FastAPI(...) → 오류 처리기 → 미들웨어 → 라우터 → 헬스체크·"/" 등록이 일어납니다. 여기까지는 "어떤 요청이 오면 무엇을 할지" 를 등록만 하는 단계입니다. 그다음 요청을 받기 직전에 lifespan 이 실행됩니다.

@asynccontextmanager                         📍 app/main.py:49
async def lifespan(app):
    await db.open_pool(settings.database_url, settings.pool_min_size, settings.pool_max_size, ...)
    yield                                    ← 서버가 사는 동안 여기서 멈춰 있음
    await db.close_pool()

연결 풀은 DB 연결을 미리 몇 개 열어 두고 요청마다 빌려주고 돌려받는 창구입니다 (📍 app/core/db.py).

왜?

왜 풀인가 — DB 연결 하나를 새로 맺는 데는 수십 ms(네트워크 왕복, 인증, 세션 설정)가 걸립니다. 요청마다 새로 맺으면 그 시간이 매번 더해지고, 동시 요청이 몰리면 DB 의 연결 수 한도를 넘깁니다. 풀은 "최소 2개 유지, 최대 10개" 로 둘 다 막습니다.

왜 wait=True 로 실제 접속을 확인하나 — 접속이 안 되는데 서버만 켜져 있으면, 문제는 첫 사용자 요청에서야 500 으로 드러납니다. 시작할 때 확인하고 실패하면 한국어로 원인(주소·방화벽·비밀번호)을 남기고 멈춥니다.

왜 빌려줄 때마다 check, 30분 max_lifetime — 회사 방화벽이나 중계기는 오래 놀고 있는 연결을 소리 없이 끊습니다. 빌려줄 때 살아 있는지 확인하고, 오래된 연결은 주기적으로 새로 맺어 "끊긴 연결로 쿼리 → 500" 을 막습니다.

왜 row_factory=dict_row — 결과를 row[2] 대신 row["sop_no"] 로 읽을 수 있어 코드가 훨씬 읽기 쉽습니다.

왜 autocommit=True 가 기본 — 조회나 한 줄짜리 수정은 바로 확정되면 됩니다. 여러 줄을 묶어야 할 때만 명시적으로 conn.transaction() 을 씁니다(19장). "묶는 곳" 이 코드에 눈에 보이게 드러납니다.

왜 timezone=UTC 세션 옵션 — 회사 DB 의 기본 시간대가 KST 든 무엇이든, 서버가 받는 시각은 항상 UTC 로 통일합니다. 응답에서도 ...Z 로 내보내고, 한국 시간 표시는 브라우저가 합니다.

왜 prepare_threshold 를 끌 수 있게 — 회사 DB 앞에 PgBouncer(트랜잭션 풀링)가 있으면 요청마다 실제 DB 연결이 바뀌어 "미리 준비된 문장" 이 사라집니다. 그런 환경이면 DB_PREPARE_THRESHOLD=0.

왜 lifespan 인가 — 풀은 서버당 하나, 시작에 열고 끝에 닫아야 합니다. FastAPI 가 그 "시작/끝" 자리로 제공하는 것이 lifespan 이고, yield 앞뒤로 적는 모양이 그 약속입니다.

3부 · 요청 하나의 여정10. 미들웨어: 모든 요청의 앞문 (②, ⑫)

요청이 서버에 닿으면 uvicorn 이 날것의 HTTP 글자를 Request 객체(요청 정보 상자)로 포장하고, 가장 먼저 미들웨어를 지나갑니다.

왜 크기 제한을 미들웨어에서 — 문서 JSON 에는 이미지가 base64 로 들어가 커질 수 있습니다. 20MB 를 넘는 요청은 바디를 읽기도 전에 헤더만 보고 돌려보내야 메모리를 아낍니다. API 마다 검사하면 빠뜨리는 곳이 생깁니다.

왜 finally 에서 로그 — 정상 응답이든, 중간에 예외로 끝났든(500) 로그 한 줄은 꼭 남기기 위해서입니다. 예외일 때는 status 가 "ERROR" 로 찍힙니다.

왜 함수 모양이 (request, call_next) 인가 — FastAPI(Starlette) 가 미들웨어를 부를 때 넣어 주기로 정한 약속입니다. call_next 는 "다음 단계를 실행하고 응답을 돌려주는 함수" 입니다.

왜 CORS 를 나중에 등록 — 나중에 등록한 미들웨어가 가장 바깥 껍질이 됩니다. CORS 가 바깥이어야 413 같은 안쪽의 즉시 응답에도 CORS 헤더가 붙어 브라우저가 오류 내용을 읽을 수 있습니다.

접근 기록(누가 무엇을 불렀나)을 남기려면 바로 이 자리에 붙입니다 → 28장.

3부 · 요청 하나의 여정12. Depends: 함수 전에 재료를 준비한다 (⑤, ⑥)

함수를 찾았다고 바로 실행하지 않습니다. FastAPI 는 먼저 함수의 파라미터 목록을 보고 칸마다 무엇을 넣을지 정합니다.

async def save_document(

    body: SaveRequest,                             ← 바디 JSON 에서 (pydantic 검사)
    user: str = Depends(current_user),             ← current_user 를 실행한 결과

user: str = Depends(current_user) 를 조각내면: user(이름) : str(타입) = Depends(current_user)(기본값 자리에 놓은 표시). 파이썬 입장에서는 기본값이지만, FastAPI 는 이 표시를 보고 "요청이 오면 current_user 를 실행해서 그 결과를 넣자" 로 읽습니다. current_user() 처럼 괄호를 붙이지 않고 함수 자체를 넘기는 이유가 이것입니다 — 실행은 나중에, 요청마다.

def current_user(request: Request) -> str:        📍 app/core/deps.py:26
    header_name = get_settings().user_header       ← .env 의 USER_HEADER (기본 X-User)
    raw = request.headers.get(header_name) or ""
    name = unquote(raw).strip()                    ← %ED%99%8D… → 홍길동
    return name or "anonymous"

current_user 의 request: Request 도 FastAPI 가 채웁니다. 이름이 request 라서가 아니라 타입이 Request 라서입니다.

왜?

왜 Depends 인가 — 없으면 API 14개마다 "헤더 꺼내기 + 디코딩 + 연결 빌리기 + 반납" 을 복사해야 합니다. 헤더 이름이 바뀌면 14군데를 고쳐야 하고요. Depends 는 공통 준비물을 함수 하나로 빼서 필요한 곳에 꽂는 장치입니다.

요청당 한 번 — API_GUARD 와 파라미터 양쪽에 current_user 가 있지만, 같은 요청 안에서는 한 번만 실행하고 결과를 나눠 씁니다.

중간에 막을 수 있음 — 의존성 안에서 예외(401/403)를 던지면 API 함수 본문은 아예 실행되지 않습니다. 그래서 권한 검사가 이 자리에 들어갑니다.

테스트에서 바꿔 끼우기 — app.dependency_overrides[current_user] = lambda: "테스트유저" 한 줄로 가짜 사용자를 넣을 수 있습니다.

왜 헤더 이름을 환경변수로 — 회사 SSO 가 어떤 이름의 헤더를 붙일지 아직 모르기 때문입니다. 코드를 고치지 않고 .env 한 줄로 바꿀 수 있게 했습니다.

3부 · 요청 하나의 여정13. get_conn 과 yield: 빌려주고, 끝나면 돌려받기 (⑥, ⑪)

async def get_conn() -> AsyncIterator[AsyncConnection]:     📍 app/core/db.py
    if pool is None:
        raise RuntimeError("DB 풀이 아직 열리지 않았습니다.")
    async with pool.connection() as conn:   ① 풀에서 하나 빌림
        yield conn                          ② 빌려준 채로 멈춤 → API 함수가 conn 사용
                                            ③ API 가 끝나면 이어서 → with 블록 종료 → 반납

return 은 값을 주고 함수가 끝나지만, yield 는 값을 주고 멈췄다가 나중에 이어서 실행됩니다. yield 가 들어간 함수를 제너레이터라 하고, 제너레이터는 "값을 하나씩 내주는 것(이터레이터)" 의 한 종류입니다. 그래서 반환 타입을 넓게 AsyncIterator[AsyncConnection]("AsyncConnection 을 비동기로 내주는 것")로 적었습니다. 더 정확하게 AsyncGenerator[AsyncConnection, None] 로 써도 맞습니다.

왜?

왜 return 이 아니라 yield — return 으로 연결을 주면 "언제 반납하나" 를 API 함수마다 직접 써야 하고, 오류가 나면 반납을 빠뜨려 풀이 말라 버립니다. yield 를 쓰면 FastAPI 가 응답 후에 yield 뒤를 실행해 주고, async with 가 오류여도 반납을 보장합니다.

왜 요청 하나에 연결 하나 — 한 요청 안의 여러 SQL(잠금, 조회, INSERT)이 같은 연결에서 돌아야 트랜잭션으로 묶을 수 있습니다.

왜 검사를 트랜잭션 밖에서 한 번, 안에서 또 한 번 — 밖의 검사는 "빨리 실패" 용(잠금 없이 싸게), 안의 검사(📍 sops.py:187 a, b)는 잠금을 잡은 뒤 "그 사이에 바뀌지 않았나" 를 확실히 하기 위해서입니다.

응답이 미들웨어로 돌아오면 로그 한 줄이 찍히고(⑫), 브라우저의 api() 가 성공이면 데이터를, 실패면 err.status·err.code 를 담은 Error 를 던집니다(⑭). 화면이 이것으로 무엇을 하는지는 25장.

왜?

왜 JSON 을 통째로 저장하나 — 편집기 화면에는 표지 FAB 체크, 레인 폭, 본문 표 칸 크기, 글꼴 크기 같은 정보가 아주 많고 계속 늘어납니다. 이걸 전부 DB 컬럼으로 만들면 템플릿 하나 바꿀 때마다 DB 를 고쳐야 합니다. 통째로 두면 편집기가 바뀌어도 DB 는 그대로입니다. 순서도 프레임(START/STEP/END, FAB 체크)을 추가할 때 DB 를 손대지 않은 이유입니다.

왜 그래도 사본을 따로 두나 — JSON 안을 뒤지는 검색은 느리고 SQL 이 복잡합니다. "이 SOP 를 참조하는 문서", "MES 를 쓰는 SOP", "Action 에 '검사' 가 들어간 단계" 같은 질문은 표로 풀어 두면 인덱스로 바로 찾습니다.

원본과 사본이 어긋나지 않나 — 사본은 저장할 때 서버가 원본에서 뽑아 같은 트랜잭션 안에서 함께 씁니다. 사람이 사본만 따로 고칠 길이 없으므로 항상 같은 버전의 같은 내용입니다. 이상한 상자는 사본에서만 건너뛰고(경고), 원본은 그대로 보관되므로 화면 복원에는 영향이 없습니다.

4부 · 데이터20. 동시 저장 충돌: 409 version_conflict

왜?

왜 "낙관적" 방식인가 — 동시 편집을 막는 방법은 둘입니다. ① 비관적: 편집하는 동안 다른 사람이 아예 못 고치게 잠금. ② 낙관적: 일단 다 고치게 두고, 저장 순간에 "내가 본 게 최신인가" 만 확인. 사내 SOP 는 같은 문서를 정말 동시에 고치는 일이 드물어서 ②가 맞습니다. 그래도 "누가 편집 중" 을 미리 알리려고 표지판 역할의 잠금(23장)을 같이 둡니다.

왜 덮어쓰지 않고 409 인가 — 나중 사람이 그냥 v5 로 저장하면, A 가 v4 에서 고친 내용이 B 의 화면에는 없었으므로 조용히 사라집니다. 409 는 "합치는 건 사람이 판단하세요" 라는 신호입니다.

base_version_no 를 null 로 보내면 — 검사를 건너뜁니다(강제 저장). 화면에서 "이미 있는 번호입니다. 그 문서의 새 버전으로 저장할까요?" 에 예를 누른 경우에만 씁니다.

  └ 없음 → INSERT / 내 것 또는 만료됨 → UPDATE (expires_at = now() + 120초)
DELETE /api/sops/{id}/lock  → 내가 잡은 것만 삭제. 남의 것/없음이어도 200 (멱등)
왜?

왜 만료 시각(TTL)이 있나 — 브라우저는 예고 없이 사라집니다(탭 닫기, 노트북 절전, 네트워크 끊김). 해제 요청만 믿으면 영원히 잠긴 문서가 생깁니다. 시간이 지나면 저절로 풀리게 하고, 살아 있는 동안은 30초마다 연장합니다. 120초 = 하트비트 4번을 놓쳐야 만료.

왜 문서 행부터 잠그나 — 잠금 행이 아직 없는 문서에 두 사람이 동시에 첫 잠금을 요청하면, "없는 행" 은 FOR UPDATE 로 잠글 수 없어서 둘 다 INSERT 로 갔다가 늦은 쪽이 중복 오류(500)를 냅니다. 항상 존재하는 문서 행에서 먼저 줄을 세웁니다.

왜 해제가 항상 200 — 페이지를 떠날 때 보내는 요청(keepalive fetch)은 응답을 확인할 수 없습니다. 이미 풀렸든 남의 것이든 오류 없이 같은 결과(멱등)여야 여러 번 보내도 안전합니다.

왜 DELETE 에 바디·쿼리·헤더 세 가지를 받나 — DELETE 에 바디를 못 싣는 도구가 있어서입니다. 다만 이것이 알려진 문제(바디 이름 우선)와 이어집니다.

6부 · 앞으로26. 사용자 식별 · 헤더 · SSO

헤더는 요청에 붙는 이름표들입니다. Content-Type, Cookie, Authorization 처럼 HTTP 표준으로 정해진 것도 있고, X-User 처럼 우리가 지은 것도 있습니다. GET 이든 POST 든 모든 요청에 붙습니다.

지금: 브라우저가 prompt 로 받은 이름을 X-User 에 넣습니다. 스스로 입력한 이름이라 아무 이름이나 댈 수 있습니다. "누가 저장했나" 기록용일 뿐 보안 장치가 아닙니다.

SSO(Single Sign-On)는 회사 계정으로 한 번 로그인하면 사내 시스템을 다 쓰는 방식입니다. 보통 서버 앞의 프록시가 로그인을 확인하고 사번 같은 정보를 헤더로 붙여 넘겨 줍니다.

  • 헤더 이름을 알면 .env 의 USER_HEADER=그이름 한 줄로 끝. 코드는 그대로.
  • 확인 방법: 회사 서버에 "받은 헤더를 그대로 돌려주는" 진단용 API 를 잠깐 두고 접속해 봅니다. 개발자 도구로는 볼 수 없습니다(그림).
  • 그다음 할 일: 프론트의 prompt·X-User 제거, 서버의 "바디 이름 우선" 제거(32장).
왜?

왜 지금 이렇게 임시로 — SSO 헤더 이름이 확정되지 않은 상태에서도 저장자·잠금 기능을 만들고 시험할 수 있어야 했습니다. 사용자 읽기를 current_user 한 함수에 모아 두었으므로, SSO 가 정해지면 그 함수(또는 USER_HEADER 값)만 바뀝니다.

6부 · 앞으로27. 권한 체계 도입

인증 (Authentication)

이 사람이 누구인가? → SSO 담당. 우리는 헤더만 읽음

인가 (Authorization)

이 사람이 무엇을 할 수 있나? → 우리 앱 = 권한 체계

인증을 믿을 수 없으면 인가도 의미가 없으니 SSO 헤더 확정이 먼저입니다.

① 역할과 표

viewer 조회 · editor 작성·저장·잠금 · admin 폐기·번호 변경·권한 관리

CREATE TABLE user_roles (
    user_id text NOT NULL,      -- SSO 사번
    module  text NOT NULL,      -- 'sop', 'opl', 'weekly'
    role    text NOT NULL CHECK (role IN ('viewer','editor','admin')),
    PRIMARY KEY (user_id, module)
);

② 검사 함수 (app/core/deps.py)

RANK = {"viewer": 1, "editor": 2, "admin": 3}

def require_role(module: str, need: str):
    async def check(user: str = Depends(current_user), conn = Depends(get_conn)) -> str:
        cur = await conn.execute("SELECT role FROM user_roles WHERE user_id=%s AND module=%s", (user, module))
        row = await cur.fetchone()
        if row is None or RANK[row["role"]] < RANK[need]:
            raise ApiError(403, "forbidden", "권한이 없습니다.")
        return user                 ← 통과하면 이름을 돌려줌 → current_user 자리를 그대로 대체
    return check

③ 거는 자리

# app/main.py — 정문
API_GUARD = [Depends(require_role("sop", "viewer"))]

# app/sop/sops.py — 방문
async def save_document(..., user: str = Depends(require_role("sop", "editor")), ...)
async def retire_document(..., user: str = Depends(require_role("sop", "admin")), ...)
왜?

왜 새 DB 가 아니라 표 하나 — 권한은 같은 DB 의 다른 표와 함께 조회되고(사용자 → 역할), 별도 DB 는 연결·백업·배포를 두 배로 만듭니다.

왜 module 칸 — SOP 는 editor 인데 OPL 은 viewer 같은 업무별 권한을 한 표로 표현합니다.

왜 역할(RBAC)인가 — 사람마다 "저장 가능, 폐기 불가 …" 를 일일이 주면 관리가 안 됩니다. 역할 몇 개를 정의하고 사람에게 역할을 줍니다. 문서 단위 권한("이 SOP 는 A팀만")은 정말 필요해질 때 추가합니다.

왜 Depends 로 — 의존성에서 403 을 던지면 함수 본문이 실행되지 않으므로, 검사를 빠뜨린 채 저장이 일어날 수 없습니다. current_user 를 품고 있으니 API 에는 require_role 하나만 적으면 되고, 요청당 한 번만 실행됩니다.

왜 프론트에서 버튼만 숨기면 안 되나 — 버튼을 숨겨도 개발자 도구에서 API 를 직접 부를 수 있습니다. 프론트는 GET /api/me 로 역할을 받아 보여 주기만 조절하고, 막는 것은 반드시 서버입니다.

추천 순서: SSO 헤더 확인 → USER_HEADER 설정 + 바디 이름 우선 제거 → user_roles + require_role → 폐기·번호 변경·저장부터 적용 → /api/me 로 버튼 제어.

왜?

왜 stdout — logging 기본은 stderr 라, 플랫폼에 따라 INFO 로그가 전부 "오류" 로 분류됩니다. 컨테이너에서는 파일이 아니라 표준 출력에 쓰는 것이 관례입니다(파일은 컨테이너가 바뀌면 사라짐).

왜 PYTHONUNBUFFERED=1 — 파이썬이 출력을 모았다가 한꺼번에 내보내지 않게 합니다. 실시간으로 보이고, 갑자기 꺼져도 마지막 로그가 남습니다.

왜 "%s" 자리 표시자 — log.info("…%s", x) 는 그 레벨이 꺼져 있으면 문자열을 아예 만들지 않습니다. f-string 은 항상 만듭니다.

왜 비밀번호를 가리나 — 시작 로그에 DB 주소를 찍을 때 mask_password 로 **** 처리합니다. 로그는 여러 사람이 봅니다.
